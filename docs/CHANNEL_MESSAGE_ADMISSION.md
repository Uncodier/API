# Channel message admission

`POST /api/agent/message` admits inbound messages; it does not generate a reply inline or select an agent from an HTTP argument. The first adapter accepts **Zavu** `message.inbound` envelopes. Do not register both URLs, change the widget, or point a Temporal generation activity at admission.

| Caller | Contract in this increment |
| --- | --- |
| Zavu's registered `/api/integrations/zavu/webhook` | Same callback, signature and acknowledgement. Message events enter the shared admission path in-process. Delivery receipts, app echoes, invitation/domain and Voice events stay on their original handlers. |
| An integration forwarding a Zavu inbound message to `/api/agent/message` | Forward the original signed body and `X-Zavu-Signature` unchanged. JSON reserialization invalidates the signature. A service key, browser session, `site_id` or `agentId` is not a substitute. Non-message events are rejected without claiming them. |
| Browser widget | `/api/workflow/customerSupport` and `/status` retain their existing visitor authorization, final-reply and asynchronous contracts. |
| Temporal execution | The existing worker calls `/api/agents/customerSupport/message` to generate an admitted reply. It must not call admission again. |
| AgentMail, Twilio/Meta, Outstand, uploads, scheduled mail | Not migrated. Identify and verify the exact inbox/number/account and replay contract before moving each adapter. |

The [receiver](../src/lib/services/zavu/receive-webhook.ts) bounds the signed body to 1 MiB and uses the same durable Zavu claim on either URL. The [adapter](../src/lib/services/zavu/webhook-handlers.ts) derives site, owner and connection server-side, checks the license, and retains the existing media handling. A missing/ambiguous binding does not start a workflow. Voice echoes do not enter the text responder. SMS and unknown channel types with a verified binding preserve inbound history only; the current worker would otherwise fall through to email.

The [handoff](../src/lib/services/channels/admit-message.ts) delegates once to the existing Customer Support workflow, preserving its FIFO scope, synchronous wait, channel metadata and queue. The work ID is derived from provider, site, channel, connection and provider message/event identity, not the agent or request time. On retry, an existing child of the same coordinator is recovered rather than re-enqueued. Previously admitted random-ID turns are **not** retroactively remapped: drain or reconcile outstanding claims before cutover. The webhook receipt and Temporal retention windows bound recovery; this is not exactly-once provider delivery.

For a new admitted text turn, `200` acknowledges a **verified disposition**, not delivery to a device: provider acceptance, a saved approval draft or a verified intentional suppression. Registered lifecycle events and intentional non-text echoes retain their existing behavior. An already-completed duplicate is not a new send. A `202` with `success:false,reconciliation_required:true` acknowledges custody **only after** the inbound claim has been marked `failed` with its original workflow ID and stage. The sender must not treat this as delivered. A lost claim or unavailable claim store returns `503`; an ambiguous historical identity returns `409`.

## Zavu receipt compatibility and cutover (local candidate)

The [bound-receipt migration](../supabase/migrations/20261121001000_zavu_inbound_claim_binding.sql) is **not deployed by this change**. The private claim table previously stored only `(provider, event_id)`, lease and status, not the tenant or sender. Its old claim RPC is not a lookup: it reopens failed and expired rows. The new service-role-only RPC leaves historical rows untouched. It adds one nullable hash and no table grants, RLS changes or backfill.

- With no event ID but a string message ID, the new receipt is in a separate provider namespace keyed by the signed sender, channel and message ID. A matching receipt is usable only with the same binding: exactly one current `settings.site_id`, one connection with the signed `zavu_sender_id` and channel, its stable `id`, the same origin message ID and signed contact. A reused key after re-binding is a conflict, not a new turn. Top-level site/account/agent hints, connection labels and array order cannot establish ownership.
- Two generations of legacy callback used the **bare message ID** and **`message.inbound:<message ID>`**, respectively. If either unbound key exists, regardless of event type or status, fallback admission returns `409` for reconciliation. A completed legacy receipt is not proof that *this connection's* message ran. Do not alter the row, resubmit with a new ID, or choose an owner from current settings. If evidence of the original turn is unavailable, leave the collision unresolved.
- Explicit event IDs and the signed-body digest keep their original `zavu` key and completed/busy behavior. Unbound failed/expired receipts cannot be retried as new work. On **any bound** failed/expired receipt, the new lease allows only lookup of the original result, never another workflow start. A crash before starting may therefore require operator review. Keep both new and historical receipts for the entire replay horizon; deleted evidence and provider replay limits cannot be reconstructed.
- For rollout, pause and drain inbound writers on **both URLs**, including in-flight old callbacks and earlier random-ID workflows. With separate authorization, verify the two historical SQL prerequisites (`20260920005000` and `20260920007000`), install only the reviewed forward migration, and verify the service-only RPC, old-writer fence and unchanged RLS. Then deploy the API including its **lookup-only recovery** path before resuming. A missing RPC and a fenced old inbound writer both fail closed (`503`); a mixed deployment is not a supported way to keep ingress available. In rollback, pause again and keep the fence and receipts; do not point live retries at an old writer.

[Signed route and disposable PostgreSQL regression](../src/app/api/agent/message/__tests__/claim-identity.test.ts): from `API`, run `node node_modules/jest/bin/jest.js --config jest.conversation-ingress.config.js --runInBand --runTestsByPath src/app/api/agent/message/__tests__/claim-identity.test.ts`. Both URLs and historical SQL run locally; this is not evidence of deployed PostgREST, Temporal or provider behavior.

## Reply on the original connection

For immediate Zavu replies, the worker sends the saved assistant message and conversation IDs. The [delivery check](../src/lib/services/channels/saved-zavu-reply.ts) follows the reply to its saved inbound message within that site and conversation. The inbound event, channel, contact, connection and provider sender must agree. Forwarded metadata is a constraint, never authority to choose a different account. A removed, rebound or disabled connection does not fall back to the site's first sender. Text retries use the same provider idempotency key for the saved reply. Provider acceptance is not confirmation of arrival.

Pinned text and native attachments share a compare-and-set on the saved assistant message **before** optional paid preparation or provider dispatch. It binds both message IDs, the authenticated sender and site, recipient, and saved payload digest. A pause during preparation may be recorded only by the owner before dispatch. Later pauses never overwrite an unknown, failed or accepted attempt. A transport timeout, unconfirmed acknowledgement or lost write leaves the original attempt intact. `queued`, `sending` and `sent` mean acceptance, never evidence of arrival; only `delivered` and `read` establish arrival.

## Reconcile the original turn; do not resend

1. Monitor failed claims and reconciliation acknowledgements on **both** message URLs. In an authorized environment correlate the durable failed claim (`private.provider_webhook_events.last_error`), `workflowId`, saved conversation/reply IDs and, where present, `send-channel-reply-<saved reply ID>`. Store no message contents, tokens or contact details in incident tickets.
2. A repeat of the **same authenticated envelope** against a bound, reclaimable receipt runs the [lookup-only path](../src/lib/services/channels/admit-message.ts). It checks the original turn, not current agent preferences or the most recent conversation. A proven failure remains failed; an unresolved attempt remains unknown, even if Temporal history has expired or a human paused the conversation afterwards. Never synthesize a new signed event to bypass claim identity.
3. Correlate provider evidence to the exact bound send. Without an unambiguous provider receipt or verified attempt, retain the hold and inspect the original provider account. An old post with only a top-level status, an unbound historical claim, or a lost response without matching independent evidence is not permission to resend. A read-only replay cannot recover an operation that provably never began: escalate rather than inventing a second turn.
4. Pause and drain old traffic, apply the bound-receipt migration only with separate authorization, and deploy the compatible API and worker before resuming. New pinned histories use `zavu-channel-delivery-outcome-v1`; previous histories retain their recorded commands. Verify two disposable connections, a changed media pin and an interrupted provider reply before enabling traffic. Keep the widget, approval flow and Voice contracts separate. These changes do **not** activate saved per-connection agent preferences.

### Signed pinned-reply lifecycle receipts

Only the registered provider callback handles [pinned delivery events](../src/lib/services/zavu/pinned-delivery-events.ts). It resolves the signed sender and channel against current settings, then checks the assistant reply and its original user message in the same site and conversation, including connection, recipient, origin IDs and saved payload digest. The envelope ID is **not** the provider message ID. A callback must carry `data.messageId` and `data.to`. If that message ID is not yet recorded, only an exact echo of the persisted random UUID (`metadata.channel_reply_attempt` on the message data or envelope) can bind it. A matching contact, content, or timestamp never binds an ID. A signed failure is stronger than a queued/sent acknowledgement; only delivery/read confirmation supersedes it. A contradictory provider ID on the same proven attempt is held for review, never substituted.

If an untagged event races the HTTP response, the callback can ask for event redelivery without sending another message. If the response was lost and the provider does not echo the attempt, a crash occurred before dispatch, an ambiguous mapping persists, or no later receipt arrives, **leave the attempt on hold for operator review**. Historical generic media and already skipped attempts are not adopted. A scoped lookup and assistant-row compare-and-set are not a transaction across settings, conversations, the original inbound row and the provider. Recovery rechecks the saved turn; there is no exactly-once delivery guarantee.

Lifecycle envelopes still use the legacy generic webhook claim, keyed by `zavu` and envelope ID (or event type plus provider message ID when there is no envelope ID). Reuse across provider accounts can make an event look busy or already complete before its handler runs. This can hide a later status, but the generic claim **never authorizes a pinned receipt** or proves that a particular tenant's send succeeded. Investigate the original receipt; do not clear claims, re-key the envelope, or resend. The [offline signed callback tests](../src/app/api/integrations/zavu/webhook/__tests__/pinned-delivery-events.test.ts) exercise the expected wire shape and failure paths, not whether Zavu actually echoes metadata or redelivers events.
