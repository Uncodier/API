# Private connector analytics: sources and operator authority

**Local implementation and offline evidence, not a deployment or a live grant.** This is a constrained reporting contract for the pinned `SUPABASE_RUN_READ_ONLY_QUERY` connector, not a general SQL proxy. Discovery advertises logical sources and column types, not project credentials, physical bindings or private rows. A request's `scope` is not an authorization. The actual human opens the receipt in their authenticated private destination; the assistant cannot read back the rows.

## Native sources

All accounts use the same connector runtime. A verified active connector must match the exact project, actor, agent and permitted operation. The **installation identity** is inferred from the existing, successful server-side catalog-actor authorization against the effective local database. An exact canonical Supabase project origin identifies itself; for a custom origin, its direct hosted CNAME and the gateway project header on that same HTTPS RPC must agree. No connector value, model input, key format or per-project environment variable establishes local identity. Missing or inconsistent evidence leaves direct analytics unavailable, not an empty report. This proof belongs to one authorization, not to a shared account cache.

| Logical source | Grain, money and dates | Tenant and supporting schema |
| --- | --- | --- |
| `analytics.paid_sales` | One `sales` row currently `completed` with an explicit `amount_due = 0`. `amount` is face value in **major** units, not a sum of cash movements. `sale_date` is the sale's business date. | Seller `sales.site_id`, not `owner_site_id`, lead, customer, buyer, user, or creator. Checked-in `makinari-db-scheme/bootstrap/supabase/migrations/20261027000118_qa_baseline_078.sql`; Stripe settlement sets `status = 'completed'` and `amount_due = 0` in `20260917210200_stripe_settlement_effect_state.sql`. |
| `analytics.tender_awards` | One approved materialized award. Values `net_amount_minor`, `tax_amount_minor` come separately from the **winning immutable procurement quotation**, not from a tender budget, order or payment. Date `created_at` is the award's creation. | `procurement_awards.site_id = quotations.buyer_site_id`; quote purpose, quote ID, tender and supplier match. `procurement_event_approvals` matches award approval, buyer site, target quotation, event and approved status. See `20261027173000_procurement_quotation_boundary.sql`, `20261027173002_procurement_orders.sql`. |
| `analytics.approved_orders` | One materialized **purchase** order with its order approval. Order `net_amount_minor` and `tax_amount_minor` are snapshots from the winning quotation. `created_at` is the purchase-order creation, not receipt or payment. | `purchase_orders.site_id` and matching award site, quotation, supplier, award ID. Approval joins the same site, order's approval ID, `event='order'`, `target_id=award_id`, `status='approved'`. See `20261027172002_procurement_event_approvals.sql`, `20261027173002_procurement_orders.sql`. |

No historical cutoff or `paid_at` is assumed. A dated paid-sale cohort reports today's saved state of sales with those sale dates, **not** a historical closing balance, payment on that date, audit of collected cash, refunds or revenue recognition. Balance-only/legacy data does not establish a dated receipt. Cancelled/refunded **sale** statuses and pending/NULL balances are not paid-sale rows; this source does not net partial refunds or check independent order fulfillment/cancellations. It is deliberately not identical to the Revenue report. Procurement does not infer a status from the date. Award and order can describe two stages of one purchase; do not add their amounts. Procurement reporting requires current owner/admin-equivalent and normal connector access. All source joins preserve tenant identity even under platform scope.

Group monetary results by `currency`; report currencies separately, with no implicit FX, default USD or cross-currency total. NULL currency is unspecified, not a currency to convert. Minor-unit columns remain integers, not major-unit amounts. Distinct account participation is `COUNT(DISTINCT site_id)` on the selected fact and interval: workspace scope yields at most one. It does **not** count registered sites, users, organizations, or the union of sites across all facts. Adding distinct counts from separate sources double-counts sites. Never infer absent data from denial or a truncated page. Example workspace query:

```sql
SELECT currency, SUM(amount) AS amount, COUNT(DISTINCT site_id) AS participating_sites
FROM analytics.paid_sales WHERE sale_date >= $1 GROUP BY currency ORDER BY currency
```

For a monthly breakdown, `date_trunc('month', column)` on a listed `date` or `timestamptz` returns the month-start date. Dates use the source calendar; timestamps use UTC, independent of the session timezone. Use half-open bounds in the same date basis as the question. For a different reporting timezone, use independently bounded intervals with explicit offsets instead of labeling a UTC month as local. The function is not a general SQL function interface. `GROUP BY` and `ORDER BY` also accept select-list positions starting at 1; a group position must refer to a dimension, not an aggregate.

```sql
SELECT date_trunc('month', sale_date) AS period, currency,
       COUNT(DISTINCT site_id) AS sites, COUNT(*) AS sales, SUM(amount) AS gross_amount
FROM analytics.paid_sales WHERE sale_date >= $1 AND sale_date < $2
GROUP BY 1,2 ORDER BY 1,2 LIMIT 25
```

This counts participating sites **per month and currency**, not unique sites over the full period. Do not add distinct counts across buckets or treat a truncated 25-row page as a complete breakdown. A local compiler rejection dispatches nothing; correct the indicated clause, keeping the original connection and scope. A platform denial is not a query syntax error.

## Workspace and platform access

- `scope: "workspace"` is the default. The site comes from the server-owned connector and private owner/instance binding; there is no model-provided site, user, project, relation or tenant predicate. Each trusted SQL source applies a bound workspace predicate, including every joined tenant edge; no model filter is relied upon. Workspace scope admits bounded non-ID fact projections, not arbitrary rows or customer columns. Platform scope is aggregate-only, excludes unattributed rows and preserves same-tenant join keys.
- `scope: "platform"` is a separate, deliberately privileged all-site action. Use only for an explicitly cross-account question; it needs **current** private connector use plus an independently issued matching grant. No implicit platform authority from a workspace owner/admin, agent, platform API credential, connection access mode, RLS bypass or token scopes. An explicit grant does not override disabled accounts, restricted members, revoked use, hidden parents or expiry.
- Operator workflow (only after approval): validate exact site, authenticated human owner, active agent, bound Supabase ref and connector/account against the intended dataset, identify the access approver and finite expiry. In the approved database-owner process, insert **one** row into `connector_result_private.analytics_grants` with `site_id`, `user_id`, `connector_id`, `agent_id`, `project_ref`, `expires_at`; record the generated grant ID. Service/browser roles cannot read or write this table and there is no grant-management RPC. It starts empty. An exact non-NULL `revoked_at` update is terminal; retire an expired outstanding grant before reissuing. Identity, expiry and grant epoch cannot be edited. Removing and re-adding a grant does not revive old reports.
- `connector_analytics_result_ready` revalidates private admission, project/source binding and active grant epoch. The runtime checks it before dispatch and again before storage. Native SQL uses `FROM ONLY` on known physical relations, strict per-relation column/type and owner checks, inactive RLS, and the exact read-only role. No original table privileges are added, and there is no new privileged function that returns business data. Failure to attest the source must not be interpreted as zero. A revocation cannot recall a provider statement already dispatched.
- Private storage rechecks authority and stamps scope, bound ref, source and grant ID independently of provider output. The authenticated owner read/list RPCs check that exact epoch on each access, in addition to existing owner/parent RLS, connector, policy/credential revision, actor grants and TTL. A revoked or expired grant cannot reopen previously saved cross-account figures. Revocation cannot recall figures already delivered to an authorized browser. Published reports from before this feature retain their original visibility and never acquire platform authorization.

## External projects: separate workspace-only contract

No automatic access to unknown shared projects, public schemas, arbitrary views, SQL, system catalogs or dynamic introspection. Direct reads require an explicit project-owner **and** deployment-operator review of permitted tenant semantics, safe analytical fields, types, base table ownership/ACL and performance. The private database registry `connector_result_private.external_analytics_datasets` stores one reviewed `(site_id, project_ref, sources)` tuple. An operator maintains that row in Makinari, not in Vercel. All eligible connections for that exact pair can use its logical facts without redeploying, but cannot access another site's mapping. No global defaults, arbitrary physical table names from the caller or cross-project inference. A synthetic policy tuple (source metadata only; no live binding):

```json
{"project_ref":"aaaaaaaaaaaaaaaaaaaa","site_id":"00000000-0000-4000-8000-000000000001","sources":[
  {"name":"bookings","schema":"makinari_facts_studio","table":"monthly","siteColumn":"workspace","money":{"currency":"currency","measures":["amount"]},"columns":[
    {"name":"amount","column":"gross","type":"numeric"},
    {"name":"currency","column":"ccy","type":"text","values":["USD","MXN"]},
    {"name":"month","column":"month","type":"date"}
  ]}
]}
```

The native names `paid_sales`, `tender_awards` and `approved_orders` are reserved. Do not publish a text category named `NULL` (reserved for a SQL null in a report). If amounts are monetary, add `money` naming the logical numeric measures and their enumerated three-letter currency column. Non-monetary numeric fields have no implicit currency. Use the unit alongside the amounts, grouping by currency when aggregating. `siteColumn` must store Makinari site UUIDs with exactly the reviewed meaning; same-looking UUIDs in another tenant model are not a contract. Produce an explicitly attributed fact table if necessary. The API checks the existing schema **and** ordinary table are `postgres`-owned; the schema must use the `makinari_facts_` prefix. No children, generated columns, active RLS (which could silently hide rows) or arbitrary functions. Only configured fields (plus count-only `site_id`) are addressed. Physical types and the reporting role's per-column SELECT privilege are verified in the same statement. Accept `numeric`, `integer` (int2/4/8), `date`, `timestamptz`, `boolean`, and enumerated `text`. Text values outside the reviewed label set become NULL; free text, client-defined mappings, joins, JSON, identity records and secrets are not accepted. The mapping does not establish data provenance: its operator is responsible for the table's content and tenant attribution. No grants or objects are created on remote projects. Without a mapping, use an explicitly published report or acknowledge no direct source is available. Never silently switch to a different project or scope.

## Rollout and verification gates

1. Obtain deployment approval. Verify the migration owner, verified project bindings, private result reader, catalog actor/location repair and mirrored SQL bytes on an approved disposable project. `20261121020000_connector_analytics_authority.sql` supplies the grant and private receipt boundary. For external datasets, apply `20261121024000_connector_external_analytics_registry.sql` before rolling out the new API. If this deployment had legacy `CONNECTOR_ANALYTICS_EXTERNAL_DATASETS`, copy each independently reviewed tuple to the registry first; the new runtime does not read that variable or `CONNECTOR_ANALYTICS_LOCAL_BINDING`. Remove old configuration on retirement and do not roll back to a runtime that could honor a revoked legacy mapping. Neither migration adds grants to `supabase_read_only_user`. Keep `connector_result_private` out of the Data API and realtime.
2. Supabase's public [role initialization](https://github.com/supabase/postgres/blob/develop/migrations/db/init-scripts/00000000000000-initial-schema.sql) creates `supabase_read_only_user` with `BYPASSRLS` and grants `pg_read_all_data`. In PostgreSQL this means a project management PAT holder with an independent raw SQL facility can read project tables, **including private report contents and grant metadata**. Ordinary table `REVOKE` and RLS do not override that pre-existing DBA-level read authority. A grant UUID is not a credential; seeing one cannot authorize a store RPC, issue/revoke a grant or change its expiry. This feature constrains the application connector path; it is not a defense against project/database admins, stolen management PATs, or a compromised service/admin. Never expose arbitrary management SQL through other assistant tools. Test raw management access separately from browser/service/assistant access; do not weaken any roles to get a result.
3. Validate physical ownership/shape, generated query bind support, plan cost and statement timeout on the intended release using authorized disposable accounts. Hosted defaults differ across versions; the runtime requires authoritative visibility of each source and fails closed on active RLS/role drift. Grouping and full-table/platform scans can be expensive. No production capacity or live provider compatibility is established by offline Jest.
4. To disable, revoke platform grants and disable catalog reads before removing mappings/disabling the connector. Removing an **external workspace** mapping prevents new calls; it does not retroactively revoke ordinary connector use for a stored workspace report. Disable connector access/advance the policy revision to invalidate those reports immediately. Native platform results always recheck their grant epoch, including after regrant.

Offline Jest: run `npm test -- --config jest.connectors.config.js --runInBand --testPathPatterns=supabase-analytics` in API. In the web repo run `npm test -- --config __tests__/security/jest.operational-offline.config.cjs --testMatch '**/connector-analytics-authority-postgres.test.ts' --runInBand`. PostgreSQL tests create and remove a fresh socket-only cluster with synthetic grants, users and private receipts. Native and external SQL tests run the actual compiled statements in isolated PGlite with synthetic facts and roles. No production credentials, rows or provider calls are used.
